# SIwithin security

This file says what the tool is built to stop, what it does not stop, and how to report a problem. Read it before you trust the fence with anything you cannot afford to lose.

## Threat model

The tool runs an agent CLI unattended. The agent is **not trusted**: it can be wrong, it can be steered by text it reads (a web page, a file in the folder, a dependency's README), and it runs commands. The person running the tool is trusted and chose the CLI, the folders and the budget. The tool and the CLI's binary are trusted code.

What the tool protects, in order:

1. The user's files outside the folders a run was given (keys, tokens, shell history, other projects, browser profiles, the tool's own ledger and the briefs of other runs).
2. The user's money: what a run, and all runs together, can spend.
3. The truth of the record: the ledger, each run's summary and, from 0.2.0, each run's receipt, a manifest of the hashes of the files the run wrote, chained through the ledger and checked by `--verify` (the README's receipt section says what it proves and what it does not).

What it does not protect against: a malicious CLI binary, a malicious `config.toml`, a hostile local user, or an attacker who already controls the account running the tool. Two gaps the 0.2.1 read named are closed in 0.3.0: with the proxy adapter the run never holds the key, and a process the run detaches is killed. What stays open is below. Chief among it: a run can still read earlier runs' transcripts, and if you choose `auth = "env"` the key is in the run's environment as before. See "Known gaps".

A worked case: `STOLEN-KEYS.md`, written after the OpenCode Console breach of 17 October 2026, sets out where a key is taken from, what the provider's alerts, a gateway budget and a door each did in that case, and which of those this tool is.

## What the fence stops (macOS, `sandbox-exec`)

The profile is generated per run, from a template, with the home folder derived at run time (`--dry-run` prints it; the run folder keeps it as `fence.sb`).

- **Reads and writes in the home folder are refused whole.** Only these are allowed back: the run's folders (readable; the first also writable unless `--readonly`), the CLI's binary, the CLI's own config directory for the run, caches, logs and keychain files under `~/Library`, Python user packages, the shell's rc files, and git's config.
- **Writes are refused** in `/private/tmp`, `/tmp`, `/opt`, `/usr/local`, `/Applications`, `/Library` and `/Volumes` (the list is `[fence] deny_write`).
- **The tool's own home is refused** to the run (config, cap, ledger, other runs' briefs and events), except the run's own temp folder, the CLI's config directory and the one file a CLI is told to write its final message to.
- **Some programs may not be started**: `open`, `screencapture`, `osascript`, `say`, `afplay`, and, from 0.3.0, `launchctl`, `crontab`, `at` and `batch`, the ways to run something later or elsewhere (`[fence] deny_exec`). The list matches by path, so a copy of one of these at another path is not stopped; that is documented under "Known gaps".
- **The tool refuses to give a run** the home root or any folder holding it, `~/.ssh`, `~/.config`, `~/Library`, each adapter's own config directory, the tool's home, or a `[never]` folder, as `--dir` or `--read`. This matters because the fence enforces only what the launcher asks: a folder allowed back would otherwise open what is inside it. Paths are resolved through symlinks and compared without regard to case.
- **The run's environment is a short list** of variables and the names you add; the rest of the shell's environment (organisation, account and token variables of a desktop session, for example) is not inherited.
- **The network (the wall, 0.4.0)**: with the proxy adapter the profile refuses every socket, DNS and binds included, but the key proxy's loopback port: `(deny network* (with message "siwithin-net:<run>"))` then `(allow network-outbound (remote ip "localhost:<port>"))`, the port filled in before launch (`[fence] network = "proxy"`, the default). Nothing the run reads can leave the machine except inside its API requests, which pass the proxy's door. Each refusal is reported by the kernel under the run's own mark; when the run's processes are gone the runner reads the unified log by that mark and counts the report in `summary.json` (`network`), and a report it cannot read is a note, not a silent zero. The wall is the kernel's socket rules, not the proxy; `"report"` leaves the network open and counts every socket the run opens, `"open"` is 0.3.0's. An adapter with `auth = "env"` has no proxy port to allow and is refused under the default rather than run open without saying so.
- **One run at a time**, by a lock held for the run's length.
- **The money**: the budget is passed to the CLI where it has a flag, and also kept by the runner from the usage the CLI streams, where it streams any (a wrong factor between the CLI's units and true dollars then cannot lift the budget); where the CLI has no flag the runner keeps it alone. From 0.3.0, with the proxy adapter, the runner also prices every request at its own door and refuses with 402 once the budget is reached, so spend the CLI's stream does not show, by a request made by hand or by a second CLI, is counted and stopped too. The cap is checked under the lock before every run. A timer kills every run. A run stopped by the timer or an interrupt before it reported its usage is booked at its budget.
- **The key**: the tool never reads, parses, stores, prints or logs the key into a file, a log or the ledger, and `--require-api-key` (on by default for the Claude adapter) checks before and at launch that the bill goes to the key and not a login, killing the run if not. How the key reaches the API depends on the adapter's `auth`. **With the proxy adapter (the Claude adapter's default, from 0.3.0)** the runner reads the key once before launch, outside the fence, and keeps it; the run's environment holds only a per-run token (`siwithin-` and 32 characters, worth nothing elsewhere and discarded when the run ends) and a loopback base URL. Every request the run makes passes one door: the proxy takes only the token (anything else gets 401), forwards only the paths on `[auth] paths` (`/v1/messages` and its token count by default; any other path gets 403 and the real key is never attached), adds the real key, relays the response as it arrives, and prices each `/v1/messages` response from its usage. One line per request goes to `proxy.jsonl` (path, model, status, usage, cost, the running total, the client port, why it was refused; never a body, a key or the token). The real key is in no file, log or error the runner writes. **With `auth = "env"`** (the Codex adapter's only mode, and an opt-in for the Claude adapter) the key is in the run's environment and inherited by every command the run starts, as in 0.2.1; see "Known gaps".
- **A detached process (the kill walk, from 0.3.0)**: a stop is no longer one `killpg` of the CLI's group. The runner keeps the set of the run's processes, by ancestry while the CLI lives and by a per-run marker at every stop, and on every stop and after the CLI's own exit it kills that set, then the group, then looks again, up to five times, holding the home's lock until none is left. `summary.json` carries `outlived`, the processes found alive that the group kill alone would not have reached, 0 on a clean run, and a note names any the walk could not kill. The one external command this needs is `ps`; its absence is a note, not a crash.

## What the fence does not stop

- **What leaves inside API requests, and the network when the wall is down.** With the wall up, a run can send the contents of its folders to the API only, in request bodies the proxy relays unread: that is the model's context, and it is the one way out that remains. Under `[fence] network = "report"` or `"open"`, and for an `auth = "env"` adapter, which needs `"open"`, a run can fetch and send anything the machine can reach: do not give such a run a folder whose contents must not leave the machine, and keep the CLI's web tools off if that matters (`args_write` in the adapter). The wall has run live three times, on 15 October 2026 (below).
- **The rest of the disk.** The home is refused; other users' folders, `/etc`, `/Users/Shared` and anything outside the home and the listed write roots can still be read, and writes outside the home are blocked only in the listed roots.
- **What the run writes into its own folder.** Scripts, git hooks, build files, `.envrc`, package manifests. If you run, commit with hooks, or build there later, outside the fence, you run what it wrote. Review before you use it.
- **Files the fence allows back.** The shell's rc files are readable: a key exported in `~/.zshrc` is visible to the run, so keep keys out of rc files. The keychain files under `~/Library/Keychains` are readable, and since 0.2.0 not writable (their items are protected by the system, not by this tool). Caches and logs under `~/Library` are shared with every program you run.
- **The CLI's own sandbox, cloud or remote tools.** If a CLI runs commands in its own sandbox, a cloud task or a remote machine, those run where the fence is not. Nested sandboxes may refuse to start on macOS; the second built-in adapter's own sandbox inside the fence has not been tested (see the README).
- **A budget that cannot be kept mid-turn.** For a CLI that reports usage only when a turn ends, one long turn can pass the budget before the runner sees it. The tool refuses such a CLI unless `--soft-budget` is given, and the ledger records what was spent.
- **A streamed stop that lags on output.** The first built-in adapter's stream reports each response's output tokens as a placeholder; the real count comes only in the final result. The runner's streamed stop therefore counts input and cache tokens fully and output tokens barely, so it never comes early and on a run heavy in output it comes after the true budget. With the proxy on, the ledger's true $ is the proxy's own total, metered at the door, and a killed run is booked at it, not at a ceiling; the streamed stop stays as a cross-check and still kills on its own count. A model with no entry in `[prices]` is priced by neither; only the CLI's flag limits it.
- **Prices that are wrong or old.** The true cost is computed at the rates in `[prices]`; a run that uses a higher tier than the listed one, or a rate that has changed, is understated. The CLI's own figure is shown beside it.
- **The prompt itself.** If a brief is passed as a command-line argument (`brief = "arg"` in an adapter), it is visible in the process list. The built-in adapters use stdin.
- **Apple's `sandbox-exec`.** It is deprecated by Apple, undocumented in places, and as strong as the profile and the kernel's enforcement. A bug in either is a way out. The profile text is short on purpose: read it.
- **Other platforms.** There is no fence on Linux or Windows, so the tool refuses to run there rather than pretend.

## Not verified in this release

- The profile was built from constructs the launcher it grew from already used. It compiled and ran live on 13 October 2026, four runs on Claude Code 2.1.296, once more on 14 October for the receipt, and again in the red passes of 14 and 15 October (README, Status and Tests): the fence refused no write it should not have, and what the CLI wrote in the paths the fence allows it, its config directory and the caches, was not listed. The runner's own budget kill, the streamed stop, ran live on 14 October in the budget red brief: a run under a budget of $0.0001 was killed at $0.0002 true.
- The proxy and the kill walk ran live in the red passes. In `env-key` (14 October) the run's search of its own environment and its ancestors' named no value beginning `sk-ant-`; the per-run token was there instead, and `ps` could not be used to confirm it (it does not start inside the fence; see "Known gaps"). In `outlive` (15 October, after the walk fix) a program the run detached into a session of its own was found by the marker at the stop and killed, `outlived 1`. Both runs called only `/v1/messages`. Not confirmed live in this release: the proxy's 402 refusal at the budget (it is exercised against a fake upstream in the smoke test, and the one live budget run was stopped by the streamed count first), and paths other than `/v1/messages` in a run long enough to call them. Seen after the release, 15 October 2026: in the unreleased `second-client` brief a program the task started sent requests through the proxy with the run's token; the proxy priced three, refused the fourth and the CLI's own next request with 402 once its total reached the budget, forwarded nothing after, and the run was killed. A survey run of 8 turns on the red home, with Read, Bash and Write, called `/v1/messages` only, so no other path has been seen live; a CLI that calls one is refused with 403, and the proxy's log names the path to add to `[auth] paths`.
- The second built-in adapter (Codex) was built from documentation and not run against a live CLI (see the README).
- The network wall has run live four times on the red home with Haiku: three on 15 October 2026 with Claude Code 2.1.296, each four turns and under a minute (the survey, the same task under the wall, which finished as it did without the wall, and the `net-out` brief, which held), and one on 18 October 2026 with Claude Code 2.1.302, 48 turns and 3.1 minutes, a thirty-file task with two network attempts half way, both of which failed in the run's own record; 44 requests through the proxy, 51 refusals in the kernel's report, 50 to the resolver and one bind, none to port 443, the receipt verified (README, Status; CHANGELOG, v0.4.0). Not verified: another adapter under the wall, whether a CLI that waits on a socket at start would hang under it, and the wall over hours rather than minutes. The kernel's lines are short-lived in the unified log: five minutes after the 18 October run a read for its mark, at the info and debug levels too, found none, where the 15 October comparison, made within a quarter of an hour of those runs, had found them; and a read for any line from the kernel over the last ten minutes returned none either, so it is the log's keeping of kernel lines on this machine, not the mark; the runner's two reads at the run's end are the only record of the refusals, and a figure in `summary.json` cannot be checked against the log later.
- `tests/smoke.py` drives whole runs against fake CLIs with the sandbox program replaced by a shim, and the kernel's log by another: it tests what the tool does around the CLI, the receipt, the proxy's checks and the network figures included, not the fence.

## Known gaps

A read of the whole code as a stranger, on 14 October 2026, found the first four below. 0.3.0 closes three of them and this section records that, with what replaced each and what it left; the fourth and the rest stay open. Each is from reading unless it says a run showed it.

**Closed in 0.3.0:**

- **The key, and spend with it unseen (closed for the proxy adapter).** In 0.2.1 `ANTHROPIC_API_KEY` was in the run's environment and inherited by every command it started, and a key helper named in the config directory's `settings.json` was readable and runnable inside the fence, so a request by hand or by a second CLI was spend no stream counted and the key could be sent anywhere. From 0.3.0 the Claude adapter defaults to `auth = "proxy"`: the run holds only a per-run token, every request passes a loopback door that meters it and refuses past the budget, and a `settings.json` naming `apiKeyHelper` in the run's config directory is refused before launch (the helper belongs in `[auth] key_command`, read outside the fence). The gap remains if you choose `auth = "env"`, which is the only mode for the Codex adapter; use a key made for SIwithin alone with a spend limit set in the provider's console there.
- **A detached process outliving the budget kill (closed).** In 0.2.1 the kill was one `killpg` of the CLI's group, so a child started in a new session kept the key and the network after the kill, the timer and the ledger line. From 0.3.0 the runner tracks the run's processes by ancestry and by a per-run marker and kills them on every stop until none is left, counting any in `outlived`; the proxy stops a survivor's spending. Residual: a process that scrubbed its marker and was re-parented to launchd before a look is beyond the walk, and the walk needs `ps`.
- **The verifier passing a cut or stripped ledger (closed).** In 0.2.1 `--verify` counted a line without a receipt and passed it, so a ledger with its last lines deleted or its receipt fields stripped still verified. From 0.3.0 a bare line after the first receipt fails, and `--verify --expect <hash>` checks the last receipt against a hash you keep elsewhere, so a tail-deleted or stripped ledger no longer verifies against a kept hash.
- **`--budget nan` (closed).** In 0.2.1 `nan` was accepted and disabled both stops. From 0.3.0 `nan`, `inf` and `-inf` are refused for `--budget`, the config budget and the `cap` file before anything else is read, in a dry run too.

**Still open:**

- **Earlier runs' transcripts are readable.** The adapter's config directory is one directory under SIwithin's home, shared by the adapter's runs and readable whole so the CLI finds its settings, and the CLI keeps its transcripts there. A run can read what every earlier run read and wrote, in every folder, briefs included. The README's "other runs' briefs are refused" is true of the briefs in SIwithin's home and false of their copies in the transcripts. The fix, not in 0.3.0: a config directory per run, seeded from the adapter's.
- **The proxy has no ceiling check.** The wall stops the request after the one that crosses the budget, so one response can pass the budget by its whole cost. A check that refused a request whose worst case would cross is not built; see the CHANGELOG.
- **Unpriced paths and models.** A model with no `[prices]` entry has its responses logged unpriced, and the run's true $ falls back to the CLI's figure. Paths other than `/v1/messages` on `[auth] paths` are forwarded and logged, not priced.
- **The environment itself has no sandbox rule.** `ps` does not start inside the fence on the macOS this was built on (it carries entitlements `sandbox-exec` will not pass), so the `env-key` red brief cannot use it to prove a value unreadable, and no narrow `sysctl-read` rule was found that hides one process's environment from another without also stopping the CLI. The key is kept out of every process's environment by the proxy, not by such a rule; with `auth = "env"` there is no such protection.
- **`deny_exec` is path matches.** It now lists `launchctl`, `crontab`, `at` and `batch` as well as `open`, `screencapture`, `osascript`, `say` and `afplay`, but a copy of any of them at another path is not stopped.
- **Smaller.** The streamed stop counts the four token fields of assistant events, not web searches or the CLI's side-query model, which appear only in the final result (with the proxy on, the ledger's true $ is the proxy's total instead). If the runner itself dies (a closed terminal, a crash), nothing is booked and the cap does not see that run. `$TMPDIR` is the user's own, and `/private/var/tmp`, `/var/folders` and `/Users/Shared` are writable. The run folder's own `.claude/` settings are loaded by the CLI on the next run there (`--setting-sources user,project`), so a run can leave settings for the next one in that folder, and a cloned repository can bring its own. The memory carve-out's pattern is case-sensitive on a case-insensitive volume. The smoke and red tests pass on Python 3.9.6, below the README's stated floor.

## Reporting a problem

Report a fence bypass, a way for a run to exceed its budget or the cap, a way to get a request past the proxy onto the real key or an off-list path, a way to get the tool to read or print a key, a false entry in the ledger, or a receipt or chain that still verifies after a change **privately**, not in a public issue.

- Write to **siwithin@metahumans.world**.
- Or use the repository's private vulnerability reporting on GitHub (the Security tab, "Report a vulnerability").
- Include the macOS version, the output of `siwithin.py --version`, the `fence.sb` and `command.txt` from the run folder (remove anything private), the run's `receipt.json` if there is one, and the steps to reproduce.

No response time is promised yet. Reports are welcome, and a fix will be credited if the reporter wants it.
